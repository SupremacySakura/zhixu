## 一、方案背景与决策记录

### 1.1 背景与定位

**毕设题目：《基于大语言模型的个人知识管理与演化系统的设计与实现》**（需求与设计见配套两份文档）。

**项目定位：知识管理为主体，网盘能力为底座。** 系统主体是个人知识管理与演化——混合检索问答、知识关联图谱、知识演化三大创新点全部落在知识管理层；cloud-drive 网盘项目（Vue3 + Go + Gin + GORM + MySQL，功能完整：分片上传/秒传、分享链接、取件码、操作日志、Docker 部署）完整复用，作为系统的文件存储与管理基础层，鉴权、上传、存储、权限隔离、任务留痕等能力全部保留，不删除任何现有功能。

**结论：一套系统，两层定位。** 论文与答辩以知识管理为主线；网盘底座体现系统工程量与完整性（具备完整存储、权限、任务管线的系统，区别于纯 RAG demo）。

### 1.2 关键决策

| 编号 | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 业务后端去留 | **保留 Go 后端** | 上传/分享/鉴权/日志是知识库的存储与业务底座能力，重写损失过大 |
| D2 | AI 工作流引擎 | **引入独立 Mastra AI 服务** | 保留 Next.js/Mastra/Vercel AI SDK 技术积累；Mastra 以独立服务模式运行（`mastra serve`），不需要 Next.js |
| D3 | 业务数据库 | **保留 MySQL 8** | 迁移 PostgreSQL 成本高收益零；中文关键词检索改用 ngram 全文索引（替代原方案的 pg_jieba） |
| D4 | 向量数据库 | **引入 Qdrant** | 替代原方案的 pgvector；Go SDK 成熟，Docker 单容器部署，与业务库解耦 |
| D5 | 前端 | **保留 Vue3** | 文件管理/分享等大量前端代码直接复用；图谱可视化用 ECharts 实现 |
| D6 | 服务拆分 | **Go 总管 + AI 服务专职计算** | Go 是对外网关与状态属主；AI 服务无状态、不碰公网、不碰 JWT |

**架构原则（继承《产品设计文档》2.2 节，仍然成立）**：

- AI 生成的任何内容不得自动覆盖用户原始内容，重要变更必须经用户确认。
- 结果可追溯：AI 回答应关联到具体文件与分块。
- 避免过度 Agent 化：固定流程使用确定性代码控制，只有需要模型理解、判断、生成的环节才调用 LLM。

## 二、总体架构

```
┌─────────────────────────── Vue3 前端（保留） ───────────────────────────┐
│   文件管理 │ 分享/取件码 │ 智能检索 │ AI 问答 │ 图谱 │ 演化中心 │ 设置     │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │ HTTPS + JWT
┌──────────────────────────────────┴───────────────────────────────────────┐
│                    Go 主服务（cloud-drive-backend，存储与业务底座）                 │
│  现有: auth │ file(分片/秒传) │ share │ operation_log                     │
│  新增: ai任务管理(ai_tasks) │ 模型配置 │ 检索API │ 会话持久化 │ 网关/代理    │
│  角色: ★ 唯一对外入口 ★ MySQL 唯一属主 ★ 任务状态机属主 ★ JWT 鉴权          │
└───────┬──────────────────────┬──────────────────────┬────────────────────┘
        │ 内部 HTTP(共享密钥)    │ 读写                  │ 读写
┌───────┴──────────────────────┐ ┌──────────────────────┐ ┌──────────────────┐
│  AI 服务（新增, Node + Mastra）│ │ MySQL 8（业务数据）    │ │ Qdrant（向量）    │
│  ingest / organize / qa /    │ │ file │ ai_tasks │   │ │ chunk 向量+payload│
│  relation / evolve 工作流    │ │ chunks │ chat_* │   │ │ (user_id 过滤)   │
│  RAG分块│Embedding│LLM调用   │ │ relations │ alerts│  │ │                  │
│  Vercel AI SDK(结构化输出)    │ │ versions │ configs│ │ │                  │
│  内部端口，不对外暴露           │ └──────────────────────┘ └──────────────────┘
└──────────────────────────────┘        ▲ 共享数据卷：原始文件
```

### 2.1 核心原则

1. **Go 是唯一的对外网关和状态属主**——鉴权、权限校验、任务状态、会话持久化、引用校验全部在 Go；AI 服务不暴露公网端口、不解析 JWT。
2. **AI 服务无状态化**——只负责"计算"（解析、分块、向量化、LLM 编排）。原始文件通过共享数据卷读取；业务数据通过 Go 的内部 API 回写。
3. **MySQL 是单一事实源**——分块记录、任务、会话、关系、演化提醒、模型配置全部落 MySQL（Go 写入）；Qdrant 仅存储向量与检索 payload，由 AI 服务独占写入。
4. **ID 全部由 Go 发放**——chunkId、taskId、alertId 由 Go 生成，AI 服务使用 Go 发放的 ID 写入 Qdrant payload。保证"引用可校验、删除可级联"（对应 SRS 6.2 第 3 条）。

## 三、服务职责划分

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 上传/下载/分享/取件码/操作日志 | Go（现有） | 不动 |
| JWT 鉴权、用户数据隔离 | Go | 唯一对外入口；所有查询强制 user_id 过滤 |
| `ai_tasks` 任务状态机、失败重试、幂等约束 | Go | 对应 SRS FR-SYS-04/05；复用现有上传幂等设计经验 |
| 模型配置存储与下发 | Go | 密钥仅存服务端（FR-SYS-03）；AI 服务经内部接口拉取 |
| 文档解析、分块、Embedding、向量写入 Qdrant | AI 服务 | 使用 Mastra `@mastra/rag` 分块策略（递归 / Markdown 专用） |
| AI 摘要/关键词/标签（结构化输出） | AI 服务 | Vercel AI SDK `generateObject` + zod schema，满足 SRS"结构化输出 + Schema 校验"约束 |
| 语义检索（Qdrant 查询） | AI 服务 | payload 强制 user_id 过滤，禁止跨用户检索（FR-QA-02） |
| 关键词检索（MySQL ngram 全文索引） | Go | Go 查询后将候选传给 AI 服务做 RRF 融合 |
| 引用校验、拒答判定、会话持久化 | Go | FR-QA-05/06 的服务端校验必须在状态属主侧完成 |
| 知识关联 / 演化判定（LLM 部分） | AI 服务 | Mastra 工作流执行，结果回调 Go 落库 |

## 四、关键交互流程

### 4.1 文件上传 → 知识化（异步）

```
前端上传 merge 成功
  → Go 创建 ai_tasks(ingest, pending)
  → Go POST /v1/ingest {fileId, userId, storagePath, mimeType} 给 AI 服务
  → AI 服务: 读共享卷文件 → 解析正文 → 分块
  → AI 服务回调 Go 保存 chunks（MySQL，获得 Go 发放的 chunkIds）
  → AI 服务: Embedding → 写 Qdrant（payload: chunkId, fileId, userId）
  → AI 服务触发 organize（摘要/标签）→ 回调 Go 写文件元数据
  → AI 服务回调 Go: 任务 success / failed（带面向用户的可读错误）
  → 前端轮询任务状态
```

失败语义（对应 SRS 8.3）：任一步失败保留已完成步骤的结果；重试具备幂等性，不产生重复分块、重复向量或重复元数据。

### 4.2 AI 问答（同步流式）

```
前端 POST /api/ai/chat（JWT）
  → Go 鉴权 → 转发 AI 服务 POST /v1/chat（携带 userId/sessionId）
  → AI 服务: Mastra RAG agent
       - 向量路：查 Qdrant
       - 关键词路：调 Go 内部接口（MySQL ngram 全文检索）
       - RRF 融合重排，取 Top N 候选
       - LLM 基于上下文生成，结构化引用 chunkId，SSE 逐 token 回流
  → Go 透传 SSE 给前端（边透传边落 chat_messages，Go 是会话唯一属主）
  → 流结束后 Go 校验引用真实存在且属于当前用户（FR-QA-05），剔除伪造引用
  → 证据不足时拒答（FR-QA-06）
```

### 4.3 演化检查（异步）

```
新知识入库成功后
  → Go 创建 evolve 任务 → AI 服务执行:
       向量近邻 + 标题相似度取候选 → LLM 对比内容输出结构化判定
       （type: duplicate / outdated / potential_conflict，含 reason 与 evidence）
  → 回调 Go 写 evolution_alerts
  → 演化中心页面展示，用户逐项审核（采纳 / 忽略 / 暂不处理 / 标记已核实）
```

演化检查设计为独立工作流，不做全库定时扫描（对应 SRS FR-EVO-01）。

## 五、内部 API 契约（草案）

### 5.1 Go → AI 服务

内部网络可达，请求头携带 `X-Internal-Token`。

```yaml
POST /v1/ingest        { fileId, userId, storagePath, mimeType }      # 异步
POST /v1/organize      { fileId, userId }                             # 异步
POST /v1/chat          { sessionId, userId, message }                 # 同步，SSE 流式返回
POST /v1/retrieve      { query, userId, topK }                        # 同步，混合检索候选
POST /v1/evolve/check  { fileId, userId }                             # 异步
```

### 5.2 AI 服务 → Go（回调）

同样以 `X-Internal-Token` 鉴权。契约约束：**持久化回调必须先于任务状态回调**，Go 校验前置数据完整性后才允许任务进入 success。

```yaml
POST /internal/ai/tasks/{taskId}/status            { status, errorMessage? }
POST /internal/ai/files/{fileId}/chunks            { chunks: [...] }   # 返回 Go 发放的 chunkIds
POST /internal/ai/files/{fileId}/metadata          { summary, keywords, suggestedTags }
POST /internal/ai/files/{fileId}/relations         { relations: [...] }
POST /internal/ai/files/{fileId}/evolution-alerts  { alerts: [...] }
GET  /internal/ai/config                           # 模型配置下发（密钥只存于 Go）
GET  /internal/files/keyword-search?query=...      # 关键词路检索（问答融合用）
```

## 六、Mastra 工作流映射

Mastra 以独立服务模式运行（不依赖 Next.js），`mastra serve` 暴露 REST 端点。原《产品设计文档》第八章的工作流设计逐条映射如下：

| 工作流 | 步骤 | Mastra / AI SDK 能力 |
| --- | --- | --- |
| `ingest-workflow` | extract → chunk → embed → 回调持久化 → 写向量 | step 编排；`@mastra/rag` 分块（递归 / Markdown 策略）；Embedding 调用；vector store 集成（Qdrant） |
| `organize-workflow` | 生成摘要/关键词/标签 → Schema 校验 → 回调 | `generateObject` + zod schema（FR-ORG-02~04 结构化输出） |
| `qa-agent` | 查询改写(可选) → 双路检索 → RRF 融合 → 生成+引用 → SSE | RAG agent；工具调用（keyword-search 工具 = 混合检索）；`streamText` 流式 |
| `relation-workflow` | 向量近邻取候选 → LLM 判定关系类型/理由/证据 → 回调 | 多 step 工作流；结构化输出；唯一性约束在 Go 侧校验 |
| `evolve-workflow` | 取候选 → 筛选 → LLM 对比内容 → 结构化判定 → 回调 | 对应设计文档 8.2 节；证据引文服务端校验在 Go 侧完成 |

配套收益：Mastra Studio（本地调试 UI）、内建可观测性与 evals，直接服务于开发与论文第六章实验。

## 八、对论文的影响

1. **新增架构素材**："业务服务与 AI 计算服务分离设计"——拆分依据、内部契约、网关模式，写入第四章系统总体设计。
2. **一致性实验素材**：MySQL 与 Qdrant 的最终一致性（任务失败重试、向量删除级联、回调乱序防护），与已有幂等上传设计呼应。
3. **降级设计**：AI 服务不可用时全链路降级——语义检索退化为关键词检索、问答返回"智能服务暂不可用"，基础网盘功能零影响。这是双服务架构的直接收益，写入第四章与第六章。

3. **答辩叙事主线**：论文以知识管理为主线（检索问答 → 关联 → 演化），网盘底座能力作为系统工程量与完整性的体现呈现；注意突出"知识演化"差异化——相对近两年常见的 RAG 问答系统，演化检测与人工审核闭环是少见点。

论文章节结构沿用《产品设计文档》第十一章目录，仅第二章相关技术补充 Mastra/工作流编排、第四章补充双服务架构设计。

## 九、风险与对策

| 风险 | 对策 |
| --- | --- |
| 跨服务调用失败导致任务悬挂 | ai_tasks 状态机 + Go 定时巡检（running 超时任务标记 failed 可重试，FR-SYS-05） |
| 回调乱序（先 success 后数据回调） | 契约规定持久化回调先于状态回调；Go 校验数据完整性 |
| 内部接口与密钥安全 | `X-Internal-Token` + Docker 内网隔离 + ai-service 不映射公网端口 |
| AI 服务整体不可用 | Go 侧熔断快速失败，基础功能零影响（双服务架构的核心收益） |
| 范围膨胀 | 严格执行 MVP 切法：先跑通 ingest → 检索 → 问答闭环，再 organize → relation → evolve；演化模块优先 FR-EVO-01 重复检测 + FR-EVO-04 版本管理 |
| Embedding 模型维度变更 | 全库向量重建，对应 SRS 2.5 假设 2，更换时系统明确提示 |

## 十、落地步骤

1. **细化内部 API 契约**：将第五章草案转为正式接口文档，作为两个服务的开发依据。
2. **脚手架**：cloud-drive 仓库新增 `apps/ai-service`（Mastra 初始化 + 最小 ingest 工作流）；docker-compose 新增 qdrant、ai-service。
3. **最小闭环**：Markdown 文件上传 → 解析分块 → 入 Qdrant → 语义检索命中。
4. **问答闭环**：接入 LLM，SSE 流式问答 + 引用校验。
5. **按 SRS 优先级推进**：organize → relation → evolve。
