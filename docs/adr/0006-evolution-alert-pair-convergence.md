# ADR-0006：演化提醒按「知识对」收敛，一条提醒可承载多个结论

- **状态**：已采纳
- **日期**：2026-11-15
- **相关**：第六章实验 4.4/4.6、[术语表](../../GLOSSARY.md)；修订 [ADR-0005](./0005-evolution-candidate-gate.md) 第 4 条「同一对只留一条」的作用范围

## 背景

第六章实验跑完 44 条知识后，库里出现 24 对知识、共 34 条提醒：10 对产生了 2 条提醒，其中 3 对的类型互相矛盾（`outdated` + `conflict`）。

原因是提醒指纹 `EvolutionDedupeKey` 由「类型 + 排序后的 ID + 证据引文」三者共同决定。同一对知识从 A 检查 B、从 B 检查 A 会各自产生一条提醒：类型可能不同，引文也必然不同（各自引自己那一侧的原文），于是两条都落库。`buildAlerts` 里「同一对只留一条」的收敛只在单次任务内生效，管不到两次独立任务之间。

对用户的影响是实质性的：演化中心对同一对知识给出两条建议，一条说「归档其一」、一条说「采纳修订」，处置互相冲突，用户无法判断该信哪条。改造后候选更容易进判定，这个问题的暴露面从 7 条放大到 34 条。

## 决策

1. **收敛单位从「证据」改为「知识对」。** 新增 `pair_key`（排序后两个知识 ID 的哈希）并建唯一索引，取代 `dedupe_key` 的唯一约束。`dedupe_key` 保留为非唯一列，用来区分「同一证据刷新」与「新证据」。
2. **按版本失效。** 新增 `pair_versions` 记录两侧 `version`。同一 `pair_key` 但任一侧版本变化时允许重新提醒，否则保持抑制。用户对一条提醒的裁决针对的是当时那两份正文，正文变了前提就不成立。
3. **一条提醒可承载多个结论。** `alert_type` 保留单值作为主结论（沿用重复 → 冲突 → 过时的优先级），新增 `payload.conclusions[]` 存全部结论，每条带自己的类型、理由、证据与建议动作。裁决动作只由主结论决定，次要结论在详情页只读展示并标注「另一侧的判定」。
4. **修订稿以较新一侧为基底。** 用 `updated_at` 判定新旧，相同则取 ID 较大的一侧，并把这条规则显式写进 `/evolve` 提示词。原实现固定写 `ids[0]`（触发侧），反向提醒时会把「以新修旧」的稿子写到较新的那条上。
5. **保留双向检查。** 不采用「只让 ID 较小的一侧发起检查」：实验里 E06、E08 正是由特定方向判对的，按 ID 掐掉一侧会把正确答案一起掐掉。方向本身是信息，收敛时用「方向 + 类型优先级」决定展示哪条。

## 理由

按对收敛而不是按证据收敛，是因为用户面对的是「这两条知识怎么处理」这一个问题，不是「这条引文算不算证据」这个问题。证据只是支撑结论的材料，不该成为提醒的身份。

保留 `alert_type` 单值而不是改成数组，是因为它已被三处依赖：列表筛选（`repository/evolution.go:61`）、首页统计（`:148`）、前端的标签与动作门禁（`EvolutionCenter.vue:99`）。改成数组会同时打破这四处，改动面远大于收益。主结论 + 结论集合的形态让筛选与统计继续可用，同时不丢信息。

按版本失效是必要的补充：只做按对唯一，会把「用户裁决过」放大成「这一对永久静默」，用户改完正文也收不到新提醒。

## 后果

- **历史数据要迁移。** 现有 34 条提醒要并成 24 条。每对优先保留仍待办的那条，没有待办就保留最新的一条；被合并掉的结论写进 `payload.conclusions[]`，若那条已裁决，把动作与备注记进 `resolution_note` 作为历史。不能简单「保留最新一条」——那会让一条 pending 提醒被一条已 dismiss 的行顶掉，用户会以为系统漏报。
- **评测口径要跟着改。** `collect` 现在按「方向」取数，一对两条提醒时靠 `subject_ids` 的顺序区分方向。收敛成一条后，方向信息移到 `payload.conclusions[].direction`，`cmd/eval/main.go` 的 `collectAlerts` 与 `direction_match` 统计都要改。报告 4.2 的 0.864 与 4.6 的严格口径 0.889 需要重算，因为分母与取数规则都变了。
- **`evolutionAllowedTypes` 的来源分派要放宽。** 一对只落一条提醒后，`updates` 强候选若同时被模型判出重复或冲突，原实现会直接丢弃该结论（只允许 `outdated`）。收敛后这类结论应作为次要结论进入 `conclusions[]`，而不是消失。
- **`refresh` 必须合并载荷，不能只刷新时间。** 现有实现（`repository/evolution.go:122-140`）对已存在的待办提醒只写 `updated_at`，`payload` 与 `severity` 原样不动。按对收敛后，反向检查命中的是同一个 `pair_key`，若仍只刷新时间，第二条结论会被静默丢弃——正是本 ADR 要解决的问题。`refresh` 需要把新结论并进 `payload.conclusions[]`、按优先级重算主结论与 `severity`，并更新 `pair_versions`。
- **结论上限的截断位置要后移。** 现在上限在模型输出清洗阶段就生效（`evolve.ts:216`、`evolve_client.go:259`），而按优先级收敛发生在 `buildAlerts` 里。截断早于排序意味着第 6 条结论无论多重要都会先被丢掉。候选上限是 8，一条任务可能合法产出 8 条结论，因此清洗阶段不应按 5 截断，应把上限留给收敛之后。
- **上限常量在两个语言里各写一遍。** `EvolveCandidateMax = 8`、`EvolveAlertMaxPerTask = 5` 与 AI 侧的 `.max(8)`、`out.length === 5` 是同一份契约的两份拷贝，改一边不会提醒另一边。用一条解析源码的断言测试把它们绑在一起。

## 备选方案

- **同一对只保留一条，新结论覆盖旧结论。** 改动最小，但用户在已裁决后又看到类型变化，像是系统改主意。
- **保留多条，前端按知识对分组。** 把矛盾原样丢给用户判断，等于没解决问题。
- **只让 ID 较小的一侧发起检查。** 看似能从源头消除双向提醒，但会掐掉特定方向才判对的样本（E06、E08），且方向信息本身有价值。
