# ADR-0003：视觉世界替换

- **状态**：已采纳
- **日期**：2026-11-12
- **相关**：[前端 UI 世界替换](https://github.com/SupremacySakura/zhixu/issues/18)（地图议题）、[方向 provenance 与视觉世界指派](https://github.com/SupremacySakura/zhixu/issues/34)、[世界参数与令牌表](https://github.com/SupremacySakura/zhixu/issues/24)、[DESIGN.md 与 design.json 骨架](https://github.com/SupremacySakura/zhixu/issues/22)、[分批实施与验收口径](https://github.com/SupremacySakura/zhixu/issues/28)、[Operate 模式下的信息层级与密度](https://github.com/SupremacySakura/zhixu/issues/21)；取代 [DESIGN.md](../../DESIGN.md) 2026-09 版的全部规范口径

## 背景

2026-09 完成过一轮前端改造，产出一份「浅色 Apple 风格设计规范」（`DESIGN.md`，279 行），并把它的条目全部落进了代码——旧文件 §7 的交付记录写的是「2026-09：已全部完成」。就「有没有按规范实现」这个问题而言，那一轮是成功的。

到 2026-11 做 UI 审计时，问题不在「有没有实现」，而在**这套设计系统没有随功能一起生长**：

| 维度       | 旧世界（2026-09 浅色 Apple 规范）                                           | 2026-11 实测                                                                          |
| ---------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 底色与卡面 | `#f5f5f7` 画布 + `#ffffff` 白卡                                             | 17 个页面全部是「白卡铺在浅灰画布上」的同一套骨架，页面之间只能靠内容区分             |
| 圆角       | 8 / 10 / 14 / 20 / full 五档                                                | 五档并存，但同层级元素取值不统一                                                      |
| 阴影       | card / popover / floating 三档柔和模糊双层                                  | 层级靠模糊阴影表达，浅灰底上对比度低，深浅关系读不出来                                |
| 字号       | 34 / 28 / 22 / 20 / 17 / 15 / 14 / 12（八档）                               | 实测被绕过成 **17 种**字号并存                                                        |
| 弹簧与动量 | `damping 1.0` / `response 0.3–0.4`；动量投影 `d = 0.998`；橡皮筋 `c = 0.55` | 参数散落在调用点，三档预设之外还有手写值                                              |
| 主色       | 品牌绿 `#10b674`（`--color-primary`）                                       | 唯一的品牌色，无第二色、无插画、无图形语言、无品牌字体、无 favicon 资产               |
| 工程口径   | 以 `tailwind.config.js` + 组件内 class 串为准                               | Tailwind 任意值 **262 处**、裸 `<button>` **196 个**、主按钮 class 串 **52 种近重复** |

结论是**世界本身**不合格，不是实现不合格：用户不满的正是「白卡铺浅灰画布」这个已被完整实现的世界。因此本条决策定性为 **redesign，不是 refinement**——refinement 的前提是底座正确、只需打磨；这里底座就是被替换的对象。

同一轮审计还发现两个次要事实，一并作为背景：一是 `tailwind.config.js` 已废弃（2026-09 起令牌迁到 `style.css` 的 `@theme`），但迁移停在半路，旧的兼容令牌 `--color-background-light/dark`、`--font-display` 仍在流通；二是 `docs/skills/apple-design/SKILL.md` 记录的是旧世界的方法论，它描述的原则（弹簧优先、毛玻璃材质、柔和阴影）与新方向直接冲突。

## 决策

1. **整份替换为「索引卡盒（Card Cabinet）」世界**，旧世界不进兼容层、不并存。世界材料：暖米白地 `#e9e5db` / 卡面 `#f2eee4` / 墨 `#181818` / 图书馆蓝 `#1f4e79` / 印章红 `#a8322a`；**零圆角**（九个圆角令牌全部归 `0px`）、1px 规则线、2px 硬偏移（无柔和模糊阴影）、Courier Prime 西文 + 系统黑体中文。
2. **规范文件整份重写而非增补**：`DESIGN.md` 从 279 行替换为 614 行 v2，按 canonical order 组织、**不设全局节号**。旧口径一律删除，不做「新旧并存」。
3. **版本状态如实标注**：v2 的 `Layout`、`States & Accessibility`、`Responsive` 三章是「**骨架 + 三章待回填**」——规则已冻结，但章首明确写着「待第一批 after-build 回填」，回填问题清单列在各章末。其余章节为已定稿。任何引用都必须带上这个状态，不得把三章骨架当作已验证结论。
4. **动效世界随替换整体作废**：`bounce` / `damping` / `response` / 动量投影 / 橡皮筋在新世界**不存在**，改为三档时长（`micro` 90ms / `standard` 160ms / `sheet` 220ms）与两条曲线（`--ease-settle` / `--ease-exit`）。`src/utils/motion.ts` 的三个导出名（`springSnappy` / `springBouncy` / `fadeTransition`）保留以避免改动 24 个调用文件，但值换成 tween；另增 `overlayIn` / `overlayExit` / `fadeIn` / `snapBack`。详见[动效语法 v2](https://github.com/SupremacySakura/zhixu/issues/29)。
5. **品牌色裁定**：旧品牌绿 `#10b674` 退役为 `--color-ai`，**只作 AI 内容标记、永不作文字色**；主色与强调色合并为图书馆蓝 `#1f4e79`。该项由[品牌资产与图标族](https://github.com/SupremacySakura/zhixu/issues/25)与[世界参数与令牌表](https://github.com/SupremacySakura/zhixu/issues/24)共同定案。
6. **迁移走「扩展—迁移—收缩」三段式**，不得直接删旧代码：批 0–1 只新增令牌与原子层（旧代码不动、视觉零变化），批 2–4 按影响范围迁移，批 5 才删兼容层，且**必须等六个页面群全完**——否则 4 个页面的 `<h1>` 会从 `text-title-1`（26px）塌成默认字号。详见[分批实施与验收口径](https://github.com/SupremacySakura/zhixu/issues/28)。
7. **方向契约不进 `docs/`**：建造期的六区块方向契约留在 `apps/zhixu-frontend/.impeccable/surfaces/` 内（当前契约文件为 `src-pages-knowledgelibrary-vue.md`，`seed:3e5b4b087e29fc24`）。`docs/` 里 `DESIGN.md` 是**建成后的规范**，契约是**建造期的临时约定**，两者不混写。
8. **三份权威的边界与冲突序**见下节。

## 三份权威的边界

本仓前端现在有三份各自被称作「规范」的文档，必须写清谁管什么、冲突时谁优先：

| 权威         | 位置                                                          | 管什么                                                                       | 谁可改                                                                               |
| ------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **产品真相** | `apps/zhixu-frontend/PRODUCT.md`                              | 用户是谁、产品让什么成为可能、定位、不可破的产品契约与实现契约、可访问性地板 | 人工审阅后修改；AI 不擅自改事实记录                                                  |
| **视觉规范** | 仓库根 `DESIGN.md`（v2）                                      | 令牌、字级、版面语法、组件、动效、状态、品牌资产                             | 人工审阅后修改；AI 可读、可在新批次中按流程回填三章                                  |
| **源头文档** | `docs/design/` 三份毕设文档（需求规格 / 产品设计 / 架构方案） | 毕设交付时的历史表述                                                         | **只有人**，且只在人工审阅后同步 `~/study/university/毕业设计/` 原件；对 AI 全程只读 |

**冲突时优先级：产品真相 > 视觉规范 > 源头文档的历史表述。**

这意味着三件具体的事：

- 视觉规范与产品契约冲突时，视觉规范错。例：产品要求「长文可读性优先于界面表现力」，则任何压缩正文行高换取版式表现力的做法无效。
- 源头文档与现行视觉规范冲突时，以视觉规范为准，源头文档按历史表述对待——它是毕设当时的记录，不是当前实现的约束。本条已体现为：`docs/design/产品设计文档.md:364` 仍写着「偏 Apple 风格的界面」，这句话在当前世界已经过时，但**不直接改**，改写建议以议题交付、由人工提交。
- 三份权威都不是「实现真相」。代码与三者不一致时，以代码为当前事实、按 `docs/brain/conventions.md` 记录差异，再由人工裁决更新哪一份权威。

产物与权威的对应关系也一并固定：`apps/zhixu-frontend/.impeccable/design.json`（schemaVersion 2，9 个组件）是视觉规范的**机器可读投影**，不是第二份规范；两者冲突时以 `DESIGN.md` 为准。

## 理由

- **refinement 会保留错误的结构。** 旧世界的问题不是配色不好看，而是「17 个页面一个骨架、零品牌资产、设计系统不随功能生长」。在「白卡铺浅灰画布」上继续打磨圆角与阴影，等于给同构样板抛光，17 个页面依然彼此不可辨。
- **替换成硬直觉的世界才扛得住增长。** 新世界的每条规则都是可判定的：圆角只有 0，「有没有圆角」不再需要讨论；容器只有四级，「宽度该取多少」不再需要讨论；颜色只有一套语义名，「这个灰是哪个灰」不再需要讨论。可判定的规范才能在页面从 17 个长到 30 个时保持收敛。
- **整份重写而不是打补丁**，是因为旧文件是围绕「材质 + 弹簧 + 柔和阴影」组织的，这些概念在新世界全部不存在。保留章节结构会保留错误的概念框架，写出来的规范会自相矛盾（例如「阴影」章还留着三档模糊值）。
- **三章留骨架是刻意的**。按 impeccable 的规矩，`DESIGN.md` 必须在第一批**构建完成之后**从已构建的世界写出来。版面、状态、响应式三章描述的是「生产页面上的实际表现」，构建前无权断言——先写满再照着实现，规范就变成「防御现实」而不是「描述现实」。
- **扩展—迁移—收缩**而非一次性切换，是因为 364 个用例与 193 处 `wrapper.text()` 断言锁住了模板结构。一次性删旧令牌会让 4 个页面的标题塌陷、让兼容层之外的其余调用点在无守卫情况下静默降级。

## 后果

- `DESIGN.md` 279 行 → 614 行，全仓唯一视觉权威。`docs/frontend-structure.md` 的「UI 与样式约定」节同步改写，旧口径（品牌绿主色、弹簧预设、兼容令牌、暗色 class 方案）**已删除**，不是并存。
- 代码内 **14 处** `DESIGN.md §2.4` / `§5.3` / `§6` 之类的陈旧章节引用**已全部失效**（v2 无节号）：`src/App.vue:15`、`src/utils/operationLog.ts:6`、`src/utils/motion.ts:4`、`src/components/ui/ConfirmDialog.vue:75`、`src/components/file-management/UploadTaskPanel.vue:61`、`:85`、`src/components/file-management/ToastNotice.vue:29`、`src/components/bussiness/SideBar.vue:50`、`src/pages/FilePickup.vue:256`、`src/pages/ChatPage.vue:81`、`src/pages/DashboardPage.vue:58`、`src/pages/HomePage.vue:69`、`:112`、`src/style.css:5`。（共 14 处、12 个文件：其中 10 处带旧节号，随替换彻底失效；另 4 处只提文件名不提节号——`operationLog.ts:6`、`SideBar.vue:50`、`DashboardPage.vue:58`、`style.css:5`——仍成立，但措辞应随批 2 一并规整。）**本 ADR 不修它们**——修注释要动 12 个源文件，属批 2 机械收敛范围。
- `docs/skills/apple-design/SKILL.md`（282 行）**不删、不改**（`docs/skills/` 对 AI 只读），但它对新规范是**反参照，不是依据**：它的十条原则里有六条（弹簧优先、速度交接、动量投影、橡皮筋、材质与深度、可打断性）与索引卡盒世界直接冲突。`DESIGN.md` 的「附录：被替换的世界」保留同一份反参照。
- 暗色模式在本 scope 内**不再保留**：`@custom-variant dark` 与 `dark:` 变体已从 `style.css` / `src/` 移除（全仓 0 处）。这是产品契约里「本次不做暗色模式」的执行结果，不是遗漏。
- `apps/zhixu-frontend/PRODUCT.md:82` 的「现行设计规范：`DESIGN.md`（279 行…浅色 Apple 风格世界）」已成陈旧表述；因 PRODUCT.md 是人工审阅产物，改由议题交付建议，不擅自改写事实记录。
- `docs/design/产品设计文档.md:364` 的「偏 Apple 风格」表述同步过时，改写建议以议题交付、**待人工提交**，`docs/design/` 全程未被 AI 修改。
- 旧 `tailwind.config.js` 的定位进一步明确：仅作迁移对照，令牌唯一来源是 `style.css` 的 `@theme`，令牌语义表以 `DESIGN.md` v2 为准。
- 仓库根 `design/` 下的 40 个 HTML/CSS 样张（`MarkdownKnowledge.html`、`Chat.html`、`DashboardPage.html` 等）是**旧视觉世界的历史样张**，只作交互结构对照，视觉口径一律以 `DESIGN.md` v2 为准。已在 `docs/markdown-knowledge-frontend.md` 的正文里标注这一点，避免被下一个读者当成视觉依据。

## 备选方案

- **refinement：保留旧世界，修圆角、阴影与字号档位**。成本最低、无需迁移，但它解决的正是「配色/细节不好看」这个伪问题，17 个页面的同构骨架、零品牌资产、17 种字号并存都不会消失，放弃。
- **并存两套规范（旧 Apple 规范 + 新索引卡盒）**：新旧页面各自成立，迁移可以无限期拖延。但两套令牌会在 `style.css` 里同时存在，任何一个新页面都要先判断「该按哪套写」，规范失去可判定性，放弃。
- **一次性切换，不做兼容层**：省掉批 0–1 与批 5。但 364 个用例与 193 处文本断言让一次性改动无法保持 CI 绿，兼容层删除后 4 个页面的标题会静默塌陷，放弃。
- **等三章（版面/状态/响应式）写满再发布规范**：看起来更完整，但那等于在构建前断言生产页面上的实际表现，规范会变成「防御现实」；且后续实现必然走向「为符合文档而妥协」，放弃。
