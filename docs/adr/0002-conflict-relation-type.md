# ADR-0002：冲突关系类型 contradicts

- **状态**：已采纳
- **日期**：2026-11-12
- **相关**：P4-W4.4 冲突识别、AC-13；修订 [ADR-0001](./0001-knowledge-relation-model.md) 的类型集合；[术语表](../../GLOSSARY.md)

## 背景

ADR-0001（2026-11-11）把关系类型定为五种：related、depends_on、supplements、contrasts、updates，并在备选方案里明确「计划里的 extends/supports/contradicts 与 supplements/contrasts 语义重叠，合并」，把 `contradicts` 并入了 `contrasts`。

一天后设计 P4 冲突识别（W4.4）时，这条合并暴露出问题：W4.4 的产出是「两条知识对同一事实给出互斥结论」，采纳后的动作是「建立一条表达矛盾的关系」。若沿用 `contrasts`，用户在图谱里看到的边标签是「对比」，与「矛盾」是两种完全不同的读法——前者表示「这是两种可选方案」，后者表示「这两条知识互相打架，至少有一条是错的」。而 AC-13 恰恰要求冲突提示可验收，把最有信息量的判定降级成中性标签，等于让验收项失去可辨识性。

## 决策

在 `relation_type` 枚举中新增第六种 **contradicts（矛盾）**：

1. `contradicts` 为**对称类型**，与 related、contrasts 一致，写入前按 min/max id 归一，同一对知识只存一行。
2. 前端中文映射为「矛盾」，与「对比」并列显示。
3. 只能由用户显式建立或由冲突提醒的 `create_relation` 动作建立；AI 关联推荐（relation 任务）**不产出**该类型——矛盾是审计结论，不是相似度能推出来的关系。
4. `contrasts` 保留原义（两种可选视角/方案），不再承担「矛盾」的语义。

## 理由

- 「对比」与「矛盾」在知识管理里是不同的动作触发：看到对比，用户会想「我该选哪个」；看到矛盾，用户会想「哪条是对的，我要改哪条」。合并后这两种行为都无法从界面区分。
- 冲突提醒的采纳动作需要落到一个可查询的关系上，P5 演化实验（冲突准确率、建议采纳率）也要按关系类型统计；若复用 `contrasts`，实验数据里冲突与对比混在一起，指标失去意义。
- 成本极低：枚举加一个值、前端加一条中文映射、术语表加一行；唯一键已含 `relation_type`，不需要改表结构，也不需要数据迁移。

## 后果

- ADR-0001 的第 2 条决策（类型取五种）被本 ADR 取代；其余决策（有向行存储、唯一键含类型、对称归一、source 列）不变。
- 「对称类型」从两种变三种（related、contrasts、contradicts），归一判重的实现分支要同步。
- AI 关联推荐的类型白名单需显式排除 `contradicts`，避免模型在 `/relate` 里自由产出「矛盾」关系——该判定只属于演化工作流。
- 图谱边标签多一种取值，图例与筛选下拉需同步（若后续加按类型筛选）。

## 备选方案

- **复用 contrasts**：不改 ADR、不加枚举，但「对比」与「矛盾」在界面和实验数据里无法区分，AC-13 的冲突验收失去可辨识标签，放弃。
- **把矛盾存成提醒而不建关系**：不污染关系类型集合，但冲突结论无法进入图谱与关系查询，用户处理完就再也看不到这条判定，且 P5 无法按关系统计采纳率，放弃。
