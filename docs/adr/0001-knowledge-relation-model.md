# ADR-0001：知识关系的存储模型

- **状态**：已采纳
- **日期**：2026-11-11
- **相关**：W3.4 关联推荐、W3.5 关系管理、W4.1 知识图谱；[术语表](../../GLOSSARY.md)

## 背景

需求规格（FR-REL-01/02/03）与计划文档对「关系」的描述并不一致，实现前必须定一份唯一口径：

| 分歧点   | 需求规格说明书                                           | phase-3 计划原文                                     |
| -------- | -------------------------------------------------------- | ---------------------------------------------------- |
| 类型枚举 | related / depends_on / supplements / contrasts（可扩展） | related / extends / supports / contradicts / updates |
| 唯一约束 | `(source_id, target_id, relation_type)`                  | `(source_id, target_id)` 唯一，反向视为同一对        |
| 来源展示 | FR-REL-03 要求边展示「AI / 人工」                        | 表结构里没有来源列                                   |

同时还存在两个隐含问题：一是「反向关系视为同一对」只对部分类型成立（「A 依赖 B」不等于「B 依赖 A」），照字面实现会把真实的方向信息压平；二是如果唯一约束不含类型，同一对知识就永远只能有一种关系，而「A 补充 B」和「A 对比 B」在语义上完全可以并存。

## 决策

1. **有向行存储**：一条关系是一行 `knowledge_relations(user_id, source_id, target_id, relation_type, confidence, evidence, status, source)`，方向由 source/target 表达，不做双向冗余行。
2. **类型取五种**：related、depends_on、supplements、contrasts、updates（界面显示相关、依赖、补充说明、对比、更新替代）。以需求规格的四型为基线，只补 `updates`，因为 P4 的过时识别（W4.3）需要一个「新版本替代旧知识」的类型；计划里的 extends/supports/contradicts 与 supplements/contrasts 语义重叠，合并。
3. **唯一键含类型**：`(user_id, source_id, target_id, relation_type)`。同一对知识允许存在不同类型的关系，但同一对同一类型只允许一行。
4. **对称类型归一判重**：只有 related、contrasts 两种类型在写入前把端点按 min/max id 排序，因此 A→B 与 B→A 视为同一对；depends_on、supplements、updates 保持严格方向。
5. **新增来源列 `source`**：ai / manual，供图谱边展示来源，也让「用户手动建立」可以覆盖一条被 AI 建议过的关系行。

## 理由

- 方向是真实信息：依赖与更新替代一旦压平，P4 的演化判定（「A 是否过时」）就失去方向依据。统一存成双向行虽然查询省事，但会把「谁依赖谁」写丢。
- 唯一键含类型让关系语义更丰富，代价是「同一对只允许一条关系」这个更简单的规则不再成立——但对知识管理产品来说，同一对知识同时存在「对比」与「补充」是合理的。
- 归一判重放在写入侧而不是数据库表达式索引：MySQL 无法对「按类型条件取 min/max」建唯一索引，且 App 层归一年成本极低（一次内存比较 + 唯一索引兜底）。

## 后果

- 查询「某知识的全部关系」必须查两次：`source_id = ?` 与 `target_id = ?`，再按方向组装视图；图谱要把有向边当作无向展示时在渲染层处理。
- 唯一键多一列后，同一对知识可能同时存在 suggested 与 confirmed 两条不同类型的关系，详情页需要按类型分组展示。
- 关系行只增不隐式覆盖：拒绝保留行做抑制；删除是物理删除（需求规格要求二次确认），删除后该知识对可再次被推荐。
- 与 plan 原文的差异（类型改名、唯一键加类型）已同步回 `docs/plan/phase-3-ai-organize-relation.md`，避免两处口径打架。

## 备选方案

- **无向表 + 双向冗余行**：查询简单，但写入要维护两行、删除要成对删，且方向信息在 depends_on 上会失真，放弃。
- **只保留 SRS 四型**：省去 P4 新增类型的迁移，但 W4.3「过时识别」只能退化成 related + 文字说明，图谱无法表达「已被替代」，放弃。
- **关系类型用字典表**：为可扩展性预留，但当前只有五种且需要前端中英映射，额外一张表换不来收益，放弃。
