# 实验报告对照代码审查：演化链路的 11 处可改点

## 背景

第六章实验报告（`毕业设计/实验/结果/实验报告.md`，论文材料，不在本仓库内）给出了检索与演化两组实验的结论与 6 条改进方向。本单以报告为线索，逐条把结论映射到 `apps/zhixu-backend` 与 `apps/zhixu-ai` 的实现，回答「代码层面还有什么可以改」。

报告已写的三条（去重键含证据、方向敏感、门槛漏检）在代码中均得到证实，不重复论证。本文重点记录报告**没有写到**的缺陷，以及每条改动的落点与代价。

## 报告未写到的缺陷

### 1. 演化候选只搜主集合，漏掉分块集合（高）

`service/evolve_task.go:213` 只搜 `vectorCollection(userID, version)`。检索链路 `service/rag.go:288-301` 会先取 `Chunks.Collections(...)`（`vectorize_tasks` 登记的全部集合）再追加主集合，演化没有这一步。

后果：重建向量期间、或分块仍落在历史集合里时，演化会系统性漏掉候选。报告 4.3 把 E10（0.503）、E13（0.571）归因为「嵌入模型区分度不足」，但其中一部分可能只是没搜到候选——两者在数据上无法区分，因为 `collect` 只记录相似度，不记录候选来源集合。

改法：候选循环套一层集合循环，`best` map 已按 knowledge 取最高分，合并逻辑不变。注意 `EvolveVectorTopK = 30` 是分块级上限，多集合下会召回更多候选，`EvolveCandidateMax = 8` 的截断会更早发生；保持 30 不变即可，截断按相似度排序。

### 2. 精确重复命中后跳过其余检测（中）

`service/evolve_task.go:113-124`：`FindByContentHash` 命中后落一条重复提醒并直接 `return`。同一批候选里的冲突与过时不会再被检查。

语义重复不走这条路（它在模型判定之后），于是两种「重复」的行为不一致：逐字重复的知识永远不会被告知冲突。

结论：保持现状。正文完全一致时「归档其一」几乎总是对的，多跑一次模型既花钱又可能给出更混乱的建议。但要在注释里写明这是有意为之，否则下次会被当成 bug 修掉。

### 3. 冲突修订稿可能写到错误的一侧（高）

`service/evolution.go:407` 固定用 `ids[0]`（触发侧）作为采纳修订的目标。反向提醒（B 检查 A）时 `ids[0]` 是较新的一条，模型给出的修订稿通常是「以新修旧」，写回去等于用旧内容覆盖新内容。

改法：用 `updated_at` 判定哪侧更新（相同取 ID 大者），把修订写到较新一侧，并把这条规则显式写进提示词。不用 `created_at`——知识被编辑后它不变，会得出反的结论。

### 4. 两条矛盾提醒的裁决不联动（中）

`service/evolution.go:303` `Resolve` 只处理当前一条。用户在 153–154 的 `outdated` 上点「标记过时」，另一条 `conflict` 仍是 pending，两条建议继续冲突。

这条随「按知识对收敛」自然消失，不需要单独修。

### 5. 上限常量在 Go 与 TypeScript 各写一遍（低）

`EvolveCandidateMax = 8`、`EvolveAlertMaxPerTask = 5`（`service/evolution.go:41,49`）与 `evolve.ts:44` 的 `.max(8)`、`:216` 的 `out.length === 5`。改一边不会提醒另一边。

改法：加一条 Go 测试，解析 `evolve.ts` 源码断言两处数字相等。不在请求体里传上限——那会把契约的约束力交给调用方。

### 6. 评测的 `evidenceLocated` 比生产侧松（中）

`cmd/eval/main.go:858` 只判断「引文能在某一侧找到」，生产侧 `validEvidence`（`service/evolution.go:128`）按声明的 `knowledge_id` 分侧校验。评测更松会让 `evidence_located` 虚高，而报告 4.1 正用它论证「AI 结论可核对」。

改法：评测改成按 `knowledge_id` 分侧校验，与生产同口径。收紧后 4.1 的 1.000 可能需要重算——如果掉下来，说明原来的 1.000 是口径松出来的。

### 7. `pairKey` 是死代码（低）

`cmd/eval/main.go:836` 定义后无任何调用点。`collectAlerts` 用的是有序方向键，这正是它需要的语义。直接删除。

### 8. 提醒去重收敛后，`refresh` 会静默丢弃新结论（高，随改动引入）

`repository/evolution.go:122-140` 对已存在的待办提醒只写 `updated_at`，`payload` 与 `severity` 原样不动。按 `pair_key` 收敛后，反向检查命中的是同一行，若仍只刷新时间，第二条结论会被静默丢弃——正是收敛要解决的问题。

改法：`refresh` 把新结论并进 `payload.conclusions[]`，按优先级重算主结论与 `severity`，并更新 `pair_versions`。

### 9. 结论上限的截断早于收敛（中，随改动引入）

上限在模型输出清洗阶段就生效（`evolve.ts:216`、`evolve_client.go:259`），而按优先级收敛在 `buildAlerts` 里。截断早于排序，意味着第 6 条结论无论多重要都会先被丢掉。候选上限是 8，一条任务可能合法产出 8 条结论，清洗阶段不应按 5 截断。

## 已达成共识的改法

三轮追问确定了以下决策，不可逆部分已写入 [ADR-0006](../adr/0006-evolution-alert-pair-convergence.md)：

1. 收敛单位从「证据」改为「知识对」：新增 `pair_key` + 唯一索引，`dedupe_key` 降为非唯一列。
2. 按版本失效：新增 `pair_versions`，任一侧 `version` 变化允许重新提醒。
3. 一条提醒承载多个结论：`alert_type` 保留单值作主结论，`payload.conclusions[]` 存全部。
4. 修订稿以较新一侧为基底（`updated_at`，相同取 ID 大者）。
5. 保留双向检查，用「方向 + 类型优先级」决定展示哪条。
6. 历史 34 条提醒并成 24 条：每对优先保留待办，无待办保留最新，被合并的结论进 `conclusions[]`。
7. 上限常量用断言测试绑定。
8. 评测 `evidenceLocated` 改按 `knowledge_id` 分侧校验，删除 `pairKey`。
9. 演化候选对齐检索的多集合搜索。

## 建议的落地顺序

按「影响用户信任」排，不按改动量：

1. **按知识对收敛**（含 3、4、7、8）。这是报告 5.2 的第 1 条，直接决定用户能否信任演化中心。ADR-0006 已记录取舍。
2. **给模型传时间戳**。代码知道谁新谁旧（`created_at` / `updated_at` / `version`），只是没传给模型。这比在提示词里加文字约束可靠，也顺带缓解报告 4.3 的方向敏感。
3. **候选对齐多集合**。改动小，但会让报告 4.3 的归因更可信——现在无法区分「没搜到」与「搜到但判错」。
4. **评测口径收紧**。会让已发布的数字变小，必须与报告一起改，不能只改代码。
5. **语义去重、换嵌入模型**（报告 5.2 第 3、4 条）。需要重跑实验，属于下一轮。

## 验证

诊断阶段只读代码，核实方式是把每条断言指回函数与行号（见上表与各条正文）。ADR 与术语表已写入，`docs/brain/` 与 `docs/skills/` 未改动。

上述第 1、3、4、5、6、7、8、9 条随后按 #55–#58 落地，见 PR #59。实现后的验证：

- `go build ./...`、`go vet ./...` 通过；`go test ./...` 10 个包全绿
- AI 服务 71 项、前端 477 项与 `typecheck` 全过
- 关键缺陷做了变异验证（改回旧实现后测试变红），确认测试不是恒真

实现过程中审查又发现三处本文未预料到的缺陷，均已修复：

- `pair_key` 的唯一索引声明在 GORM tag 上，`AutoMigrate` 会在回填前把它建在历史空值上导致启动失败；`pair_versions` 用 `not null` 的 JSON 列追加到已有表会触发 `ERROR 3140`
- `mergeConclusions` 与 `primaryConclusion` 排序口径不同，导致 `alert_type` 与 `conclusions[0]` 不一致，前端标错主结论
- `outdatedSubject` 固定取 `SubjectIDs[1]`，合并后会把较新的一条标记为过时

## 残余风险

- **报告在仓库外且未同步。** 报告仍是旧口径，与本文的结论存在已知差异，需人工誊写；数字需按新口径重跑后更新。
- **E10/E13 的真实原因未知。** 候选集合漏搜是合理怀疑，但没有数据能证实，需要先补采集候选来源集合。

## 教训

- **「已实现的收敛」要区分作用域。** `buildAlerts` 里的 `seen` 看起来是去重，实际是任务内去重。跨任务去重只能靠数据库约束，代码里的 map 管不到并发的两次任务。
- **报告归因与代码能力要分开核对。** 报告把低相似度归因为嵌入模型，但代码在召回阶段就可能漏掉候选；两者在现有数据上不可区分，这不是报告的错，是采集口径缺了字段。
- **写回目标不能固定为「触发侧」。** 双向检查下「触发侧」不等于「较新侧」，任何写操作都要先确定语义方向，再选 ID。
- **按证据去重的注释会随语义变更而过时。** 收敛单位从证据改为知识对后，旧注释里的「幂等键是类型 + ID + 证据引文」全部失效；实现完成时要回头清理这类描述，否则下一个读者会照着旧规则理解代码。
- **并行实现的接缝要有可执行的核对。** #56 与 #58 并行开发，文本无冲突但语义冲突（#56 删掉截断后 #58 的契约测试匹配到了别处），只有跑测试才能发现。合并时"无冲突"不等于"无问题"。
