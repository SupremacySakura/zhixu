# 前端视觉世界替换（索引卡盒）的文档收口

## 背景

前端 17 个页面共用的是一套 2026-09 完成的「浅色 Apple 风格设计规范」：`#f5f5f7` 浅灰画布上铺白卡，圆角 8/10/14/20/full，三档柔和模糊阴影，damping 1.0 弹簧配动量投影（d=0.998）与橡皮筋（c=0.55），主色品牌绿 `#10b674`。这套规范**已经全部落地**——问题是它落地之后就再没长过：功能从 6 个页面涨到 17 个，设计系统仍是同一套「白卡铺浅灰画布」骨架，配色、圆角、阴影、字号档位全是模板默认值，零品牌资产。诊断数据很硬：262 处 Tailwind 任意值、17 个字号并存、196 个裸 `<button>`、主按钮 class 串有 52 组近似重复。

这说明坏的不是实现，是**世界本身**——所以定性为 redesign 而非 refinement，整份替换为「索引卡盒（Card Cabinet）」：暖米白 `#e9e5db` 地 / `#f2eee4` 卡面 / 墨 `#181818` / 图书馆蓝 `#1f4e79` / 印章红 `#a8322a`，零圆角、1px 规则线、2px 硬偏移，Courier Prime 西文 + 系统黑体中文。

本单（GitHub [#23](https://github.com/SupremacySakura/zhixu/issues/23)）处理的是替换之后**文档层的收口**：新规范已于[前序任务](https://github.com/SupremacySakura/zhixu/issues/22)写进 614 行的 `DESIGN.md` v2 与 `design.json`，但仓里同时存在三份相互矛盾的口径——旧 `docs/frontend-structure.md` 仍说主色是品牌绿、旧 Apple 规范仍被当成依据、`docs/design/` 三份毕设文档仍写着 Apple 风格。本单把这批口径一次性理清，并把「哪份文件管什么」写成可执行的边界。

## 教训

- **「设计系统没随功能增长」比「配色不好看」更是真问题。** 一开始的直觉是换个配色、调调圆角，但诊断数字（262 任意值 / 17 字号 / 196 裸 button / 52 组近似 class 串）指向的是另一件事：系统有 6 个页面时建的骨架被 17 个页面继续套用，没人再回头扩系统本身。前者是审美品味问题，改一次就完；后者是资产随规模失配，不换世界修不掉。判断标准可以固定成一句：**问「功能涨了三倍，设计系统涨了吗」，而不是问「好看吗」**。
- **把方向裁决交给掷骰脚本，能绕开模型自己的审美偏好。** 方向由 `concept-seed --scope direction --mode operate` 掷出（`ASSIGNED INDEX: 7`，`seed:3e5b4b087e29fc24`），脚本给出七种候选与三种材料族。因为结果是**掷出来的**，模型无法事后把自己的偏好伪装成论证——「我喜欢米白所以我选米白」这条路被物理堵死。用户最终推翻了骰子选了索引卡盒，这个推翻也因此是有意识的人类裁决，而不是模型悄悄夹带。可复用的做法：凡是「选一个方向」这类无法用事实证伪的决策，先交给随机源，再让人覆盖。
- **规范要在构建之后再写。** 先写规范再照着实现，写出来的是一份「防御现实」的东西——它描述的是作者希望的界面，落地时每一条都要打折，最后规范变成一叠打不赢的愿望清单。这次反过来：先由图版切片（27 张 = 3 视口 × 3 视图 × 3 变体）与令牌实测（WCAG 51/51 类生成）把世界跑通，再回头写 `DESIGN.md`，写的时候是在**描述已经存在的东西**。代价是三章只能留骨架（Layout / States & Accessibility / Responsive 待第一批 after-build 回填），但这恰好是诚实的：**能写实的地方写实，写不实的就明说写不实**，比先把三章编满再打折可控得多。
- **「旧口径删除而非并存」这条纪律需要主动执行。** 同步文档时最省事的做法是把新口径追加在旧口径旁边，读者自行判断；这次是逐句删掉旧的。并存等于把裁决成本转嫁给下一个读者（很可能是 AI），而 AI 读到两份矛盾口径时的行为是不可预测的——它可能按顺序取第一条。单一信息源原则（`docs/brain/conventions.md` §4）真正的成本就在这里。
- **只读目录的价值在于它逼你把改动写到别处。** `docs/design/` 三份毕设源头文档不许 AI 改，于是 `产品设计文档.md:364` 那句「偏 Apple 风格」只能以「改写建议」的形式交付给人。这个约束看起来碍事，实际效果是逼出了「原句 → 建议改为 → 为什么改」这种可审阅的格式，比直接改文件更有用：人拿到的是决策材料，不是既成事实。
- **规范写完不等于落地，文档必须显式记落差。** `src/utils/motion.ts` 到今天仍是旧弹簧值（`bounce: 0` / `bounce: 0.2`），`.vue` 模板仍是旧字号。如果文档只写「是这样」，下一个人（或 AI）读代码时会以为文档错了。所以 `frontend-structure.md` 专门写了「以规范为准，不要照抄现存代码」，并在 ADR 里列出 14 处失效的 `DESIGN.md §x.y` 注释——**不修它们，但要记录它们的存在与归属批次**。

## 可沉淀模式

- **权威分层与冲突序**：一份项目里的「真相」超过一份时，必须写明每份管道什么、谁可改、冲突时谁赢。本次定的是 `PRODUCT.md`（产品真相）> `DESIGN.md`（视觉规范）> `docs/design/`（源头文档的历史表述），并把 `design.json` 明确定性为「机器可读投影，不是第二份规范」——避免机器产物被当成可以反向覆盖人写规范的权威。
- **方向决策的三段式**：随机源给出候选与指派 → 人覆盖或接受 → 落成方向契约文件（本次在 `.impeccable/surfaces/`，六区块 THESIS/OWN-WORLD/STORY/FIRST VIEWPORT/FORM/FINISH）。契约不进 `docs/`（它是构建期工作产物，不是项目知识），但要在 ADR 里记下路径与 `seed`，让方向可复现、可追溯。
- **扩展—迁移—收缩（expand–migrate–contract）**：规范整体替换时，先加兼容层和原子层（视觉零变化），再分批迁移调用点，最后等所有调用点迁完才删兼容层。本次的关键约束是「批 5 必须等六个页面群全完」——因为 4 个页面的 `<h1>` 依赖兼容层的 `text-title-1: 26px`，提前删会让字号塌成默认值。任何「先删旧再补新」的方案都会在这里翻车。
- **规范版本状态要如实标注**：`DESIGN.md` v2 明确写「骨架 + 三章待回填」，每章章首写「待第一批 after-build 回填」并列回填问题。文档不假装完整，读者（含 AI）才不会把骨架当定稿去引用来论证。
- **引用规范用章节名而非节号**：v2 用 canonical order、没有全局节号，所以引用写成「见 `Motion` 章」。这让章节可以增删重排而不产生一批失效引用——旧世界的 `§2.4` 正是反例，替换后有 14 处注释集体失效。
- **改写建议的交付格式**：「原句 → 建议改为 → 为什么改」三段式，写进 issue 评论而非直接改文件。适用于任何 AI 只读目录。
